# Nexus 枢纽 v0.1.6

这一版四件事：把 nginx 少配的压缩与缓存规则补上、修掉"界面说 ≤4 MB 但 2 MB 就被挡"、
修掉重复审批会多出一篇草稿的竞态。

## 性能：终于开了压缩

nginx 之前**没有任何 gzip**，HTML/CSS/JS 全按原样传。`/static/app.css` 37,620 B、
`htmx.min.js` 51,076 B，每个首次访问的成员都要完整下载一遍。现在开了
`gzip`（`gzip_types` 显式列出 `text/css`、`text/javascript` 等——nginx 默认只压 `text/html`）：

| 资源 | 压缩前 | 压缩后 | 省 |
| --- | --- | --- | --- |
| `/` | 4,404 B | 1,665 B | 62% |
| `static/app.css` | 37,620 B | 10,253 B | 73% |
| `static/htmx.min.js` | 51,076 B | 16,677 B | 67% |
| `static/editor.js` | 6,461 B | 2,683 B | 58% |

## 修复：2–4 MB 的图片永远传不上去

界面与 `DESIGN §32` 都写着"图片 ≤ 4 MB"，应用侧也按 4 MiB 收；但 nginx 的
`client_max_body_size` 是 `2m`，**2 MB 以上的请求在 nginx 就被它自带的 413 页挡掉了**，
应用根本没收到。改成 `5m`（4 MiB 图 + 表单余量），应用层的限制才是唯一真相。

## 修复：并发"通过投稿"会多出一篇草稿

`approve_submission` 的顺序是"事务外读状态 → 建草稿（kb 自己的事务）→ 回填投稿行"，
中间有窗口。两个管理员同时点"通过"（或一个人双击）会各建一篇草稿，回填只有一个成功，
于是库里多出一篇没人认领的重复文档。现在先 `SELECT … FOR UPDATE` 锁住那条投稿再动手，
第二个请求等到锁释放时状态已不是 `pending`，直接 409。

新增的测试用两个并发 future 钉住它：修复前实测 `left: 2, right: 1`（两篇草稿），修复后只能建出一篇。

## 其他

- `/static/` 响应里原本有两条互相矛盾的 `Cache-Control`（`expires 30d` 与 `add_header` 各写一条，
  `max-age` 分别是 2592000 与 31536000），只保留后者。
- 动态页面加 `Cache-Control: no-store`：退出登录后按"后退"不该还能看到上一个账号的页面。
- 修掉 `add_header` 继承陷阱：`/static/`、`/uploads/`、`/downloads/` 里自己加了 `add_header` 之后，
  server 级的 `X-Frame-Options` / `Referrer-Policy` 会被静默丢掉，现在各层都显式声明。

## 验证

`cargo test` 262 项全绿（新增并发审批用例），`clippy -D warnings` 与 `fmt --check` 均 0；
线上冒烟 19/19，压缩与上传上限都在真实链路上复测过。

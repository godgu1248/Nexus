## IPv6 让「按 IP 限速」形同虚设

注册、登录失败、整地址上限这三个限额都按客户端地址计键。IPv4 上没问题，**IPv6 上等于没有上限**：
一台普通 VPS 或一条家宽带一整个 `/64`（2⁶⁴ 个地址），服务端只能看到一个个"新"地址，每一发都是第一次。

后果有三层：注册限额失效等于开放了一个不需要登录的 argon2 消耗点（19 MiB + 两次迭代）；
登录失败限额失效等于撞库从"每 5 分钟 5 次"变成"每 5 分钟无限次"；
计数表被灌满后还会触发淘汰，把别人的桶挤出去——顺手替别人清了限额。

现在地址先归并再计数：

```
2001:db8:77:1:aaaa::1  ┐
2001:db8:77:1:bbbb::2  ┘  →  2001:db8:77:1::/64   （同一个额度）

203.0.113.7            →  203.0.113.7
::ffff:203.0.113.7     →  203.0.113.7
```

`/64` 是运营商分给一个用户的最小单位：`/48` 会把不同客户并到一起（一人被限速、邻居遭殃），完整地址等于没限。
IPv4-mapped 地址会还原成 IPv4，否则所有 v4 会被并进 `::/64` 一个桶。

## 验证

| 检查 | 结果 |
| --- | --- |
| 单测 | 同 `/64` 不同后缀落一个桶、不同 `/64` 互不影响、v4-mapped 还原、不可解析串原样透传 |
| 线上探针（直连应用端口） | **8/8**：A 连错 5 次未锁 → 换同 `/64` 另一地址即被锁 → 换另一个 `/64` 不被锁 |
| `cargo test` | 312 passed / 0 failed |
| clippy `-D warnings` / fmt | 0 / 0 |

## 关于验证方式，一点说明

同样的探针走公网域名会得到"无关地址也被锁"的假象——因为 nginx 的
`proxy_set_header X-Real-IP $remote_addr;` 会覆盖客户端自带的同名头，所有请求在应用看来都是同一个地址。
这不是缺陷，正是之前那次防伪造修复在起作用。**要验证分桶逻辑，必须绕开反向代理直连应用端口。**

## 仍然记着的两件事

- 拥有大量 `/64` 的攻击者仍可能靠淘汰挤掉别人的桶（按用户 ID 计键的上传/评论/投稿不受影响）。
- 会话存储达到上限时的淘汰会连带清掉活跃会话（表现为"莫名要重新登录"）；真要治，得从"只给匿名访客签发 CSRF 会话"入手，而不是调大上限。

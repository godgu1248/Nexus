# Nexus 枢纽 v0.1.8

本轮审查看的是「数据库有没有替我们守住不变式」和「浏览器会不会把不该留的东西留下」。

## 修复：同一个人可以同时有两条待处理的加入申请

原来的护栏是「先查有没有 pending，再插入」。两次并发点击都能通过这条检查，
于是库里出现两条 pending：管理员看到重复条目，批准一条之后另一条还挂在队列里，
而这条幽灵申请会一直占着「已有待处理申请」的位置。

现在把不变式放进数据库：`join_requests` 加一个生成列 + 唯一索引。

```sql
pending_user_id = IF(status = 'pending', user_id, NULL)   -- 生成列（STORED）
UNIQUE KEY uk_join_pending (pending_user_id)
```

`NULL` 不参与唯一性比较，所以同一个人仍然可以有多条 approved/rejected 历史，
但任意时刻最多一条 pending。第二次并发插入会撞 1062，被翻成 409 而不是 500。

迁移里**先清掉已有的重复 pending**（保留最新一条）再加索引：不然 ALTER 会因违反唯一索引失败，
而迁移失败会让新二进制在启动阶段直接拒绝起来——那是最难查的一类故障。

## 新增：页面一律 `Cache-Control: no-store`

这些页面里带着 CSRF token 和「当前是谁」。允许缓存至少有两个后果：

- 共享电脑上，按一次后退就能看到上一个人登录时的页面；
- 会话轮换（`cycle_id`）之后缓存的 token 必然失效，用户看到的是「操作失败」，而日志里什么都没有。

`/static/*` 由 nginx 直出、根本不经过应用，所以静态资源的强缓存不受影响。

## 修复：置顶没有实际变化也写了一条审计

`set_pinned` 的 UPDATE 带 `<>` 守卫，重复点同一个按钮返回「没改动」。
原来的代码不检查这个返回值，照旧写一条 `kb.doc_pin`——审计的意义是「谁在什么时候改变了什么」，
把无变化也记进去，只会让真正的那一条更难找。现在没改动就直接回滚并返回。

## 顺手修掉一条会随机变红的分页测试

它翻的是 `/lobby`——全站公开议题的合并列表。并行用例随时往里插新议题，
排序一变，「两页不重叠」就会变红：这不是页面错了，是断言把「并发插入」当成了「分页重叠」。
改成翻自己分区（`/forum/{slug}`）的页，分页机制与全量列表是同一套代码。
